# B1 · 上下文网络（头姿 + 手持物）—— 设计、资源估算与风险

> 2026-10-16 · 目的：在**不推翻已验证成果**的前提下，为「分心」与「抽烟/打电话」
> 提供 AI 能力，并给出**可验证的资源预算**。
>
> 结论先行：**放得下（LUT ≈65%），但时序是主要风险**；
> 且**不能**做成"一个网络吞掉所有任务"，理由是数据（见 §1）。

---

## 1. ★★ 为什么不是"单个网络吃掉眼态+头姿+手持物"

原计划写的是「共享 backbone + 眼态/头姿/手持物三个头」。**算进去之后必须改**，
原因不在资源，在**数据**：

| 资产 | 形态 | 新网络能不能用 |
|---|---|---|
| **CEW**（1040 个被试的闭眼） | 单眼 patch（整图当人脸框裁出的眼方块） | ❌ 换成"人脸 ROI 48×48"输入就用不了 |
| **MRL**（红外，37 人，预训练） | 单眼 patch | ❌ 同上 |
| 板上 5 人的 6 万条 | 单眼 patch（`crop_square` 输出） | ❌ 同上 |

**CEW 那 1040 个跨人闭眼样本是当前跨人泛化证据的全部来源**（`open`/`invalid` 只有 5 人）。
把眼态任务并进一个新网络，就要用**人脸 ROI** 当输入，这些数据**全部作废** ——
在只剩约 4 周的情况下，等于把"跨人泛化 0.9525 / 五折留一法"这套证据推倒重来。
**不值得。**

⇒ **正确的形态是两个网络**：

```
眼睛 patch 32×32 ──► eye_cnn_accel（**现有，一行不改**）──► 闭/睁/无效
                      └ 跨人数据（CEW/MRL/板上）全部继续可用

人脸 ROI 48×48 ────► context_cnn（**新增**）──┬─► 头姿 4 类（分心）
                                             └─► 手持物 4 类（抽烟/打电话）
```

"多任务"落在**新网络内部**（头姿与手持物共享 backbone、一次推理出两个结论），
而不是去合并已经验证过的眼态网络。

**代价**：每帧多一次推理（约 4.6 ms）；PL 多一个网络。
**收益**：现有成果零损失；新网络可以独立降规格、独立回退。

## 2. 网络结构（context_cnn）

对齐 `EyeNet-3C` 的写法（SAME 卷积 + 2×2 maxpool，全 1-D 展平，`ap_ctrl_hs`）：

```
输入：人脸 ROI 灰度 48×48（int8 量化域 q = g' − 128）
 conv1  3×3, 1→8,  SAME, ReLU    → maxpool 2×2 → 24×24×8
 conv2  3×3, 8→16, SAME, ReLU    → maxpool 2×2 → 12×12×16
 conv3  3×3, 16→24, SAME, ReLU   → maxpool 2×2 →  6×6×24  (= 864)
 fc1    864→32, ReLU
 ├─ head_pose    32→4   （正对 / 左 / 右 / 低头）
 └─ head_object  32→4   （无 / 手机 / 烟 / 其他）
```

两个头**各自独立 FC**，共享 fc1 之前的一切 —— 这就是省资源的关键。

| | eye_cnn（现有） | context_cnn（新） | 倍数 |
|---|---|---|---|
| 输入 | 32×32×1 | 48×48×1 | 2.25×面积 |
| 通道 | 8 / 16 / 32 | 8 / 16 / **24** | conv3 小 25% |
| **参数** | 22,403 | **32,672** | 1.46× |
| **MAC** | 680,032 | **1,355,008** | 1.99× |
| 输出 | 3 类 | 4 + 4 类（两头） | — |

MAC 明细（可复核）：

```
conv1  48·48·(9·1·8)   = 165,888
conv2  24·24·(9·8·16)  = 663,552
conv3  12·12·(9·16·24) = 497,664
fc1    (6·6·24)·32     =  27,648
heads  2·(32·4)        =     256
                        --------
                        1,355,008
```

## 3. 资源估算

**方法**：用 `eye_cnn_accel` 的**实测增量**当锚点外推，而不是信 HLS 的 `csynth`
（已知它偏悲观约 2 倍：估 15,927 LUT、实测增量 7,500）。

锚点（`impl_1` 报告，加 CNN 前/后对比）：**+7,500 LUT / +50 DSP / +13 RAMB36**。

| 资源 | 现有整设计 | context_cnn 估计增量 | 相加后 | 占比（xc7z020） |
|---|---|---|---|---|
| Slice LUT | 26,663 (50.1%) | **+7,000 ~ +9,500** | ~34,000~36,000 | **64% ~ 68%** |
| DSP48E1 | 86 (39.1%) | **+45 ~ +65** | ~131~151 | **60% ~ 69%** |
| Block RAM | 46 tiles (32.9%) | **+6 ~ +8**（参数多 46%，权重 ROM 按比例） | ~52~54 | **37% ~ 39%** |

**外推依据**：
- 参数 1.46× → 权重 ROM 按比例涨（当前 CNN 占 13 个 RAMB36，估新网络 ~19 → 增量 +6）；
- LUT 由**卷积器并行度 + 行缓冲 + 控制**决定：通道数少了 25%，但输入宽度从 32 → 48
  使行缓冲与地址逻辑变大，两者大致抵消，**净变化估计 +5% 以内**；
- DSP 与并行乘加器数量相关，大致随通道数走（略降），但输入更大可能让 HLS 选择更多并行。

⚠️ **这三行是估计，不是实测**。LUT 的不确定性最大（±20%）。
**必须用一次 `csynth` 做相对比较**（§7 的下一步），最终仍以 `impl_1` 报告为准。

### 延迟

延迟与 MAC 数近似成正比（同一套循环结构）：`2.329 ms × 1.99 ≈ **4.6 ms**`。
加上更大的 `load_padded` 开销，估 **4.5 ~ 5.5 ms / 次**。

对系统的影响（当前整循环 31 ms / 32.3 FPS）：

| | 现在 | 加 context_cnn 后 |
|---|---|---|
| 每帧 CNN | 2 × 2.42 = 4.9 ms（双眼） | 4.9 + ~4.6 = **9.5 ms** |
| 整循环 | 31 ms (32.3 FPS) | **~36 ms（约 28 FPS）** |

★ 注意：**28 FPS 恰好顶到摄像头采集上限 28.5 fps** —— 也就是说再加东西就会
成为新的瓶颈。**这个余量要留给后面的功能**（或者按 §5 的杠杆降规格）。

**可分期**：手持物（抽烟/打电话）与头姿是**两个头**，可以**先只上头姿**
（`head_object` 先训成常输出"无"，PL 里那部分 FC 代价可忽略），确认整链路 OK
再加第二个头 —— 因为头的开销本来就很小，真正的成本在 backbone。

## 3.1 ✅ 2026-10-17 骨架实测（C 仿真 + csynth）

**产出**：`hls/context_cnn/context_cnn.cpp` + `_tb.cpp` + `hls_config.cfg`；
权重/测试向量由 `eye_cnn_ml/gen_context_hls.py` 生成（**随机权重**，
只验证整数语义，不是训练产物）。

**C 仿真**（`sh build_csim.sh context_cnn`）：4 个用例、7 层激活 + 8 logits
与 `quant_ref.py` 金标准**逐位相同**；几何自检双向通过。
⚠️ 第一次生成时移位量把中间激活压成了 0，4 个用例的 logits **完全相同**，
逐位比对照样 PASS —— 这是典型的"假 PASS"。已把随机规格调到非零激活，
并在 `gen_context_hls.make_cases()` 里加了"logits 不能全相同"的断言，
`eye_cnn_ml/tests/test_context_spec.py` 也有专门用例。

**csynth**（xc7z020clg400-2，10 ns，`v++ -c --mode hls`）：

| | eye_cnn | context_cnn | 倍数 |
|---|---:|---:|---:|
| 延迟（周期 / ms） | 232,882 / **2.329** | 456,047 / **4.560** | 1.96× |
| LUT | 15,929 | 18,034 | 1.13× |
| DSP | 54 | 63 | 1.17× |
| BRAM_18K | 42 | 70 | 1.67× |
| FF | 11,005 | 12,124 | 1.10× |
| 流水线最大 `ap_enable_reg_pp0_iterN` | 22 | 25 | 正常 |
| csynth 时序估计 | — | **7.300 ns**（uncertainty 2.70） | 满足 10 ns |

- **延迟与 §3 的估计完全一致**（4.6 ms）：MAC ×1.99 的线性外推成立。
- LUT/DSP 的相对增幅与"参数 ×1.46、MAC ×1.99"同一量级；按 eye_cnn
  已知的 csynth 悲观系数（估 15,927、实际增量 7,500，约 2×）反推，
  实际增量约 +8.5k LUT，落在 §3 的 +7.0k~+9.5k 区间内。
- ⚠️ **BRAM 的纸张估计偏乐观**：csynth 从 42 → 70（+28 个 18K =
  +14 RAMB36），而 §3 估的是 +6~8。原因是激活缓冲随输入面积涨得比
  权重大（`ca` 8KB→18KB、`xpad` 2.6KB→5.4KB）。按同一悲观系数折算，
  整设计 BRAM 约 **39%~43%**（文档原估 37~39%），**仍然放得下**。
- **时序仍是最大风险**（§4 不变）：csynth 只说明 100 MHz 下逻辑级数
  可控，真正的 WNS 要看实现后的 `clk_fpga_0`。

**未做**：没改 BD、没重出 bitstream、没上板。IP 已打包进
`V2_ov5640_hdmi/ip_repo/context_cnn_accel/`，但**尚未例化**。

**下一步**：按 §7 —— 资源/时序已确认 → **可以开始 B2 采数据**；
训练后再用 `export_weights.py` 覆盖同名头文件，kernel 不用改。

## 4. 时序风险（★ 这一版最大的风险）

当前 `clk_fpga_0`（100 MHz，三个自研 IP 都在这个域）**WNS = +0.512 ns** —— 余量很薄。
再加一个网络，**WNS 很可能转负**。

应对顺序：

1. **先切 `clk_fpga_0` 的余量来源**：跑一次新 bitstream，看 `Intra Clock Table` 里
   `clk_fpga_0` 的 WNS 与**失效端点路径**（是 CNN 还是 AXI 互联）；
2. 若转负且在 CNN 内部：加 `#pragma HLS PIPELINE II=2`（吞吐减半、时序宽松，
   CNN 从 4.6 → 9.2 ms，**仍在预算内**）；
3. 若在 AXI 互联：拆 Interconnect 层级或给自研 IP 单独走一条；
4. 最后手段：**把 `clk_fpga_0` 降到 80~90 MHz** —— ⚠️ 但这会同时拖慢 HDL 视频链路
   的 AXI 侧，**必须先确认 VDMA 的带宽余量**（28.5 fps × 921 KB × 2 通路 ≈ 52 MB/s，
   对 100 MHz 32 位来说不算紧，但要实测）。

**别烧时序不收敛的 bitstream**：会把板子带进坏状态，换回好版本也救不回来，必须重启
（这个坑已经踩过一次，见 `hls-per-pixel-division-blows-up-pipeline`）。

## 5. 降规格杠杆（按代价从低到高）

如果 `csynth` / `impl` 显示装不下或时序崩了，按这个顺序砍：

| # | 杠杆 | MAC 变化 | 代价 |
|---|---|---|---|
| 1 | 输入 48×48 → **40×40** | −31% | 手部信息变少（仍能看到脸侧/嘴前的手） |
| 2 | `fc1` 864→32 改 **864→16** | −0.5%（可忽略） | 分类能力略降，**但省 LUT**（FC 的 27,648 参数占总参数 85%） |
| 3 | 通道 8/16/24 → **6/12/18** | −44% | 需要重训；容量下降 |
| 4 | 砍掉 `head_object`，只留头姿 | −0.02% | **抽烟/打电话做不了**（但头姿=分心仍成立） |
| 5 | 输入降到 32×32 | −56% | **手基本看不到**，手持物必然做不了 |

★ 注意 #2：**FC 层占了总参数量的 85%**，而 MAC 只占 2%。
如果想省 **BRAM**（权重 ROM），砍 `fc1` 的宽度比砍卷积有效得多 ——
这与直觉相反，值得在综合前先试一版。

## 6. 与现有系统的接口（要做的事）

### 6.1 几何：`canonical.py` 加一个函数（几何单一真源）

现有 `square_bounds(roi)` 是给**眼睛方块**用的。人脸 ROI 需要新增：

```python
FACE_CROP_K = 2.00      # 人脸 ROI 边长 = K × face_h（2026-10-18 已标定冻结）

def face_square_bounds(face_box, k=FACE_CROP_K):
    """以人脸框中心为中心、边长 k×face_h 的方块（人脸 ROI）。"""
```

**必须与训练侧共用同一个函数**（否则又是"训练裁剪 ≠ 部署裁剪"）。
标定方法沿用 `crop_calib.py` 那套**目视**流程（自动指标测不出取景对错，
这个坑已经踩过）。

⚠️ `FACE_CROP_K` 决定"能不能看到手"——**先做 §3.6 的取景实测**再定：
手在画面里 → k 取小一点（1.6）；手在画面外 → k 再大也没用。

### 6.2 `img_preproc` 必须改（第二个风险点）

现有模式 1 写死输出 **32×32、两个 patch（左右眼）**。新网络要 **48×48、一个人脸 ROI**。

三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| A. 加"模式 2" | 改 kernel 支持 48×48 人脸 ROI | 要重综合 + **重做逐字节比对**（`test_img_preproc.py`），风险中等 |
| B. 借道现有模式 1 | 把 48 当"放大的眼睛方块"塞进去 | ❌ 几何语义完全不同，是 hack，不要 |
| C. **PS 裁剪缩放** | 灰度已在 PS 手里（`gray` 640×480），直接 `cv2.resize` | **零 PL 改动**，代价 ~2~3 ms/帧（与当年 PS 裁剪的 3.02 ms 同量级） |

★ **建议先走 C**：它不动已上板验证的 PL，能立刻把 B 阶段跑通；等整条链路验证过
再考虑搬到 A（那时有充分的回归测试垫底）。**这是"先用最不容易出错的路把功能做出来"
的一贯做法。**

### 6.3 采集端：一份采集要能出两种方块

`collect_eye_patches.py` 现在只存眼睛 patch。要加存**人脸 ROI 方块**（同样是
`crop_square` 变换前的原始像素），这样：

- 眼态网络的训练数据（CEW/MRL/板上眼睛 patch）**继续可用**；
- 上下文网络的训练数据**同步积累**，不必单独再采一遍。

段协议直接复用（`open:30,closed:30,left:20,right:20,low:20,phone:20,smoke:30`）——
**标签同一份，两个网络各取所需**。

#### ✅ 2026-10-18 已实现（`collect_eye_patches.py --context`）

- **默认关**，不传 `--context` 时眼态采集行为逐位不变。
- 同一帧同时落两种方块：眼睛 patch 仍进 `raw/` + `patches.csv`；
  人脸 ROI 进 **`raw_ctx/` + `context.csv`**（单独的文件/目录 —— 两类标签语义
  不同，混在一张表里会让 reader 分不清）。
- 几何单一真源：`canonical.face_square_bounds()` / `crop_face_square()` /
  `face_square_fully_inside()`。方块中心 = 人脸框中心，边长 = `int(face_h × K)`，
  **越界返回 None（不补齐）** —— 边缘复制出来的条纹是合成内容。
- `FACE_CROP_K` 已于 2026-10-18 **标定冻结为 2.0**（第一版数据全部按 2.0 采集）：
  启动时先用 `--debug` 看 HDMI 上的
  青色方框（红框=越界），确认手/手机在框里；越界计数会写进 `session.json`
  （`ctx_out_of_frame`），越界多于写入时会当场警告。
- **段 → 标签**：

  | 段 | 头姿 | 手持物 | 眼态 |
  |---|---|---|---|
  | `open` / `closed` / `blink` / `normal` | forward | none | 按原证据链（normal 只产 open） |
  | `left` / `right` / `low` | left / right / down | none | **不产**（头动了，2D 眼 ROI 不成立） |
  | `phone` / `smoke` / `other` | **None** | phone / cigarette / other | **不产** |
  | `invalid` | — | — | 原无效类路径 |

  `phone`/`smoke` 不监督头姿，是因为打电话/抽烟时头姿不固定，硬标 forward
  会把真实侧脸喂进 forward 类 —— 那是**制造标签冲突**，比少一个监督信号糟。
- **换段静默期** `--ctx-seg-settle 1.0 s`：自动协议换段后操作者要过一会儿才
  转头/拿手机，不跳过这段会把过渡帧标成目标类。
- 其他参数：`--context-crop-k`（默认 2.00）、`--ctx-min-interval`（0.5 s）、
  `--ctx-min-side`（48）。
- 建议协议（`--list-protocol` 第二张表）：
  `normal:30,left:20,right:20,low:20,phone:30,smoke:30,other:20`。
  约 10 FPS、0.5 s 间隔时每段约 2 条/秒；**每类 300 条通常要跑 2~3 轮**
  （多换光照/坐姿/距离，别靠调小采样间隔凑数）。
- PC 侧 QC：`eye_cnn_ml/context_qc.py --montage`（每类 64 张 montage +
  几何一致性检查 + CSV/PNG 数量核对）。
- 测试：`tests/test_context_collect.py`（17 项，纯逻辑/几何）+
  `tests/test_collect_run.py` 新增 7 项（假硬件跑通 `run()`，验落盘/CSV/越界/
  静默期/默认关）。

### 6.4 PL 侧：新增 `context_cnn_accel`

- 地址：`0x41900000`（`eye_cnn` 是 `0x41700000`，`img_preproc` 是 `0x41800000`）；
- 挂 `axi_smc` 的下一个空闲从口（`S03_AXI` 已被 `img_preproc` 占用 → 用下一个）；
- ⚠️ `ps7_0_axi_periph` 的 `NUM_MI` 增一**必须补 `M0x_ACLK/M0x_ARESETN`**，
  不接会静默永久复位（真踩过，见 `vivado-tcl-and-ip-gotchas`）；
- ⚠️ 换 IP 后 **`refresh_eye_cnn_ip.tcl` 那一步不能省**（Vivado 工程自己存着一份
  IP 副本，VLNV 不变时会锁住旧版、**静默拿旧权重再综合一遍**）。
